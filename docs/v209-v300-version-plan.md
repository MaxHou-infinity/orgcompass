# OrgCompass v2.0.9 → v3.0.0 版本规划（Version Plan）

> 项目：`orgcompass`（React 18 + TS strict + Vite 8 + Tailwind 4 + Tauri 2）
> 当前基线：**v2.3.1（已发布）**；目标：**v3.0.0**
> 文档性质：**排期基线**。本文档给出 v2.0.9 → v3.0.0 的版本切分与各版本开发重点，供后续排期与设计评审；不等同于发布日期承诺。
> 关联路线图：[v208-roadmap.md](v208-roadmap.md)（v2.0.8 三视角）、[v209-roadmap.md](v209-roadmap.md)；v2.1.1 / v2.2.0 / v2.3.x 的路线图与契约文档为本地内部归档（未随仓库公开发布），此处不作链接。
>
> **落地情况（2026-09-18 回填）**：v2.0.9 / v2.1.1 / v2.2.0 已按本规划交付；实际发布线中另插入 v2.0.10—v2.0.12（体验与布局修复）、
> v2.2.1（体验收敛）、v2.3.0（排兵布阵可用化：看板整合 + 岗位缺口清单）、v2.3.1（事实与口径收口）。v3.0.0 仍未启动，需独立评估需求与数据条件。

## 0. 定位与切分原则

v2.0.8 已完成「信任与稳定性收口」（xlsx 高危处置、Tailwind 4 / Vite 8 迁移、CI/发布硬化、导入护栏、诊断口径说明、企业阶段预设）。从 v2.0.8 到 v3.0.0 的本质是**产品范式升级**：

- v2.x 定位：**组织架构设计工具**（画布 + 树 + 组织健康度）。
- v3.0.0 定位：**排兵布阵 + 人才胜任度看板**（围绕「人岗匹配」的决策工具，从评估「组织健康度」升级为评估「排兵布阵健康度」）。

因此版本切分遵循三条原则：

1. **先补口径、再换模型、再上算法、最后整合看板**——依赖关系决定顺序，不可颠倒。
2. **每个版本独立可发布、独立可回滚、有可量化验收**（沿用 v2.0.8 纪律，不把跨层改动捆绑）。
3. **不提前做「定义债」未清的算法**——胜任度算法、领导力评分、人岗匹配状态机需先出设计文档，再进实现版本。

| **视觉与治理** | 红黄绿灯贯穿员工层、每一层胜任度/空缺岗位看板、招聘 BP 直读、权限/隐私/评价偏差/人工复核 | §3.2.1 / §3.2.5 / §5 |

### 2.3 关键依赖链（决定排序）

```
口径修正(v2.0.9：纯 analytics + UI + 测试，独立)
        │
岗位数据模型(v2.1.1) ──→ 胜任度引擎(v2.2.0) ──→ 排兵布阵看板(v3.0.0)
        │                     │
        └─ 招聘缺口视图(前置)  └─ 人岗匹配状态机(前置载体)
```

岗位模型是胜任度与招聘视图的地基；胜任度算法是排兵布阵看板的数据源。中间两个 minor **顺序不可颠倒**。

## 4. v2.1.1 —「岗位化」（minor，V3 地基）

### 4.1 为什么是 minor 且风险最高

这是从「组织结构设计」迈向「人岗匹配」最关键、也最危险的一步。岗位（Position）实体是胜任度引擎与招聘视图的共同前置。数据模型改造会牵动导入、画布、健康度、`.orgproj` 迁移四处，必须独立、可回滚、带迁移测试。

### 4.2 开发重点

| # | 范围 | 说明 |
| --- | --- | --- |
| A | **Position（岗位）实体** | 新增岗位模型，编制 `headcount` 从部门级下沉到岗位级；旧 `.orgproj` 无损迁移 |
| B | **人岗匹配状态机** | 进图 / 未进图 / 超编 / 不胜任 的判定与展示（V3 §4 数据可追溯性硬约束） |
| C | **富字段导入** | 员工 Excel 支持「编制 / 个人成本 / 目标职级」列，替代逐人 `window.prompt` 职级差距（HR 审计「数据字段对齐」是最大断点） |
| D | **招聘缺口与成本视图**（招聘 BP 第一步） | 复用 L3 `gap`/`gapCost` 做部门缺口汇总卡/表格 |
| E | **`leaderType` 负责人类型** | 闭环 v2.0.9 遗留的「副职/挂名精确剔除」（管理者比分子只计正职） |
| F | **AI 主数据就绪**（前瞻） | 稳定 ID / 显式外键 / 结构化枚举 / 时态快照 / 原始派生分离，为未来 AI 分析岗位·组织·胜任度预留（本版本不做 AI 功能） |

### 4.3 验收出口

- [x] 旧 `.orgproj` 文件无损迁移，岗位级编制可正确算空岗率。—— 已交付；v2.3.1 补上「迁移同时对齐名册」的修复。
- [x] 导入可一站式带入编制/成本/目标职级，来源数字与系统一致。—— 已交付（员工表内嵌岗位/成本/目标职级/直接上级；独立「岗位表 sheet」按 §4.4 决策裁剪，未接 UI）。
- [x] 人岗匹配状态（进图/未进图/超编/不胜任）可判定、可展示、可追溯。—— 已交付（`match.ts` 状态机 + 画布标记 + 看板）。

### 4.4 来自 v2.0.9 推迟清单的合并判断

> 逐条复核 [v209-roadmap.md](v209-roadmap.md) §1.2「推迟」清单（v2.1.1 路线图 §11 有完整复核记录，该文档为本地内部归档）。

| v209 推迟项 | 是否纳入 v2.1.1 | 去向 |
| --- | --- | --- |
| 副职/挂名精确剔除（`leaderType`） | ✅ 纳入 | §4.2 补充：**E `leaderType` 负责人类型**（闭环 v2.0.9 遗留） |
| N 场景自由组合对比矩阵 | ❌ 仍推迟 | 岗位化稳定后单独做 |
| 场景合并 / 归档 | ❌ 仍推迟 | 状态管理复杂度高，后置 |
| 差异「优劣自动评判 / 方案推荐」 | ❌ 永不 | 违反「只陈述事实、不黑盒评分」红线 |

| 行业基准引擎 | ❌ 长期挂起 | 需跨企业样本标定，维持「先做阶段，行业留后」 |

**结论**：仅 `leaderType` 纳入 v2.1.1；其余维持推迟或明确不做——岗位化本已是大重构，避免范围失控。
