> 作者：hr-expert（团队 v208-roadmap）· 面向"真正把工具用于职场诊断与汇报"的 HRBP/OD 用户。
> 依据当前仓库实测（`src/utils/analytics.ts`、`src/utils/excel.ts`、`src/components/{HealthDrawer,DiagnosticReport,OnboardingOverlay}.tsx`、`src/types/index.ts`、`README.md`、`docs/v208-roadmap.md`）。凡引用代码均给出位置，便于核对。

## 0. 一句话结论

v2.0.8 若只做工程收口，HR 用户拿到的是「**可用但不放心**」：数据被安全解析、能跑通、能出图，但——

- **4 项指标的失真点完全不透明**，HRBP 可能把「平均管理幅度 6 人·适中」直接写进管理层汇报，而背后其实藏着一个 40 人直管部门；
- **未配置编制的部门会显示成黄色"关注"**，被误读为"有问题"，与 README 承诺的"不伪装结论"矛盾（这是信任问题，不是小瑕疵）；
- **导入字段与 HR 手里的编制/成本/目标职级表对不上**，真实诊断需要人手补录，容易和来源系统数字打架；
- **示例/行业模板全是绿色无诊断感**，首次体验看不出工具价值。

建议：**把 0 成本、纯配置/文案的 3 个小项并进 v2.0.8**——①诊断口径说明、②按企业阶段的"情景基准"预设、③未配置数据的状态呈现修正。它们不增加工程负担（不依赖 xlsx 替换、不动数据模型），却直接消除上面 ① ② ③ 的信任与上手风险。其余 HR 能力（导入富字段、招聘缺口视图、职级差距导入）排到 v2.0.9。

## 1. 指标口径审计表（潜在失真 / 误读点）

### 先摆代码事实（口径如何被算出来）

| 指标 | 当前口径（代码位置） | 关键细节 |
| --- | --- | --- |
| 管理幅度 | 有负责人部门的 **直属员工总数 ÷ 有负责人部门数**（analytics.ts L371-390） | ①只统计**有负责人**的部门；②"直属员工"取 `d.employees`（该节点**直挂**员工，L376），**不是整棵子树**；③跨部门取**平均** |
| 层级深度 | 树从 L1 起的 **最大** 路径层数（`computeTreeDepth` L452-458） | 取全组织**最大值**，一条深链即决定全组织结论 |
| 管理者比 | **去重**(按 leaderId 或 leaderName)的部门负责人数 ÷ **员工总数**(L360-418) | 分母 `totalEmployees` **包含管理者本人**、也包含未配置编制部门的员工；分子只认"被设为部门负责人的 key" |
| 空岗率 | (**抽查编制合计** − **全量员工**) ÷ 抽查编制合计（L429-441） | 编制只累加 `headcount>0` 的部门；员工数却取**全量**（含未配置编制部门的员工）——**分子分母口径不一致** |
| 超编 | \|缺口\| ÷ 实际人数（L302-304、L317） | 不区分"战略性超编"与"冗余" |
| 未配置编制 | deptStatus 对 `headcount===null` 返回 **warn**（L314） | → 部门显示黄色"关注"；但对应的诊断建议是 **info**（L746-755） |

### 逐项审计

#### A. 管理幅度（"每经理平均直管人数"）
**失真点**
1. **平均被极端值稀释**：一个 40 人直管部门 + 若干 2 人部门，平均可能落在"适中"区间，掩盖单点失控。口径把"健康"建立在**算术平均**上，对长尾极其敏感。
2. **只看有负责人的部门**（L373-374）：如果一个**大部门没有设负责人**，它既不进分子也不进分母，从管理幅度里**凭空消失**。
3. **只算"节点直挂员工"，非整棵子树**（L376，测试 L120 也明确"只计直属下属，非子树"）。在**多层级导入组织**里，员工是**落在叶子节点**的（excel.ts `buildDepartmentTree` L152-176：按部门路径匹配到最深一层），所以中间管理层（如"研发部"负责人）节点上往往只有他自己，其下属都挂在更低的叶子节点 → **中间管理者直管人数被系统性低估**，很容易误报"管理幅度偏窄""负责人无人直管"（critical，L678-687）。

**适用 / 不适用的阶段**
- 适用：**扁平、单层、IC 直接挂部门**（初创、小团队），此时平均直管有参考意义。
- 不适用：**多层科层组织**（制造业、医院、教育、成熟集团），此刻"直属（节点内）"≠"真实直管"，建议按**下一层子部门负责人数 + 节点直挂 IC 数**计。

**风险提示**
- 对 HRBP 最大的坑是 **"负责人无人直管"的 critical 提示** 在真实多层组织里会被高频误触发，降低报告可信度；
- 平均口径会让一个"宽到失控"的部门被"其它很窄的部门"抹平。

**建议口径修正**
- 至少：把"管理幅度"标签下面的说明写成**"有负责人部门的平均直管人数"**，并**同时给每个有负责人部门的直管数**（部门级明细已有，见 `generateDeptSuggestions`），让极端值可见。
- 更优：管理幅度改用 **"负有负责人部门的直管中位数 + 最大/最小"** 展示，避免平均被稀释；或把直管定义为"下一层子部门负责人数 + 节点直挂 IC"。

#### B. 层级深度（树最大层数）
**失真点**
- 用全组织**最大**路径（L452-458）。一条"总部-事业部-中心-区-门店"的深链，会把整个组织判为"层级过深"，即使 90% 的部门只有 3 层。**少数深链部门被当成全组织结论**。

**适用 / 不适用阶段**
- 单一"健康 ≤4"的阈值是**一刀切**。零售连锁/区域-门店型、医院、教育集团天然更深（总部-区域-门店/校区），**4 层内反复触发"偏深"**；而这些组织的深度往往是**业务需要**，不是问题。

**风险提示**
- 用"最大层数"下结论，会诱发 HRBP 无区别地"压层级"，反而破坏成熟链条型组织的必要纵深。

**建议口径修正**
- 同时展示 **P50 / P90 层数 + 最大层数**，并标注"最深链路出现在哪个部门"；阈值按**阶段情景**分档（见 §2），而非一个全局 ≤4。

#### C. 管理者比（负责人数 ÷ 员工总数）
**失真点**
1. **未剔除兼岗 / 副职**：产品里"兼岗"有 `isVirtual` 虚拟员工，但**管理者比没有把"兼岗负责人"与"专职负责人"区分**——一个身兼两部门负责人的人，去重后只算 1（L363-364），口径看似"去重"了，但**不知道他是否真的是管理者，还是挂名**。
2. **分母含管理者本人**（L367 `totalEmployees` 是全部非虚拟员工，含这些负责人自己）：所以这个比例是"管理者 ÷ (含管理者的全员)"，**不是"管理者 ÷ 非管理者"**。在 200 人组织里若有 30 个管理岗，比值 = 15%，但按"每几个非管理员工配一个管理者"算其实是 30÷170≈17.6%。**两者口径不同，HRBP 对"管理者占比"的常规理解往往是后者**。
3. **分子可能引用组织外的人**：负责人若由 `leaderId`/`leaderName` 指向一个**不在员工表里、或不在当前范围内的外部 VP**，它会记入管理者数、却不在分母员工数里 → **抬高比值**。

**适用 / 不适用阶段**
- 适用于**管理层与员工能同一张表**、且负责人都是内部员工的组织。对"负责人含外部/上级"、或"挂名负责人"多的组织会失真。

**风险提示**
- 比值偏高容易触发"头重脚轻"，但真实原因可能是**兼岗负责人**或**外部负责人**，而不是官僚化。

**建议口径修正**
- 明确分母为"非管理员工数"，并在说明里写清"管理者÷员工总数（含管理者）"的当前语义（避免歧义）；
- 引入"负责人类型"（专职 / 兼岗 / 外部 / 挂名）到部门数据，管理者比只计**专职**并**仅当负责人在员工表中**。

#### D. 空岗率（(编制−实际)/编制）
**失真点**
1. **分子分母口径不一致**（L421-441）：编制只累加 `headcount>0` 的部门，员工数却是**全量**（含未配置编制部门的员工）。若存在大量"没填编制"的部门，其员工会把空岗率**压低**（显得招聘很健康），掩盖真实缺口。
2. **对"编制是否真实"极度敏感**：编制若是**虚设 / 因业务转型而保留**的"僵尸编制"（headcount 为满足预算而填，实际不招），空岗率会**虚高**，误导招聘节奏。产品无从判断编制真实性，只能靠 HR 自己填真实数。
3. **超编不分性质**：`overStatus` 只按 |缺口|/实际 >20% 判预警（L302-304），不区分"战略性超编"（为业务扩张提前储备）与"冗余超编"。

**适用 / 不适用阶段**
- 适用于**编制经过真实验证**的**成熟/成长组织**；对处于**业务转型、编制虚设、或创业者未规范化填编制**的阶段，这一指标最不可信。

**风险提示**
- 空岗率最容易被"编制数是否靠谱"绑架。**编制没填 → 显示黄色关注（L314）**，此时它不是在说"你空岗多"，而是在说"你没查"——但黄灯会让 HR 误读为"有问题"。

**建议口径修正**
- 空岗率的**分母只取"已配置编制部门的员工"**，与编制口径对齐；
- **未配置编制 → 显示灰色"无数据"+ 一句话原因**（而非黄色关注），对应 README 承诺；
- 在超编建议里补充提示"请确认是战略储备还是冗余"。

## 2. 阶段 / 行业基准是否提前进 v2.0.8

**判断：倾向合理，但建议只做"企业阶段情景基准"这一个可切换预设，暂缓"行业基准引擎"。**

理由：
- README「Next」承诺的是"可复用的行业/企业阶段**诊断基准**"。这是一个**多年期、需要跨企业样本**的能力，收益远低于它占用的工程成本；v2.0.8 以工程收口为主，不应被拖入。
- 但只给**企业阶段（初创/成长/成熟）三档预设**是**低风险、高可信度**的：它本质就是往现成的 `HealthThresholds` 结构（analytics.ts L113-130）里填 3 组值，加一个"情景基准"切换器，**数据模型不用动**。成本几乎全在配置与文案。
- **已有"行业模板"（industryTemplates.ts）与"诊断基准"是两回事**：前者是**组织形态模板**（几个部门怎么摆），后者是**红黄绿阈值**。营销/文档上要**明确区分**，否则用户会误以为"行业模板=行业基准"。

### 推荐阶段划分与预设基准值（可给区间）

当前 `DEFAULT_HEALTH_THRESHOLDS`（L133-145）大致落在"成长"档——这解释了为什么**它天然对初创偏严、对成熟偏松**（初创 3 层常被误判偏深；成熟 5-6 层常被误判过深）。

| 指标 | 初创（<100人·探索/验证） | 成长（100-1000·规模化） | 成熟（>1000·稳态/矩阵） |
| --- | --- | --- | --- |
| 管理幅度健康区间 | 2–7（允许更紧；创始团队直管少） | 4–8（默认档，**≈当前**） | 5–9（流程成熟可容纳更宽） |
| 管理幅度关注上限 | 10 | 12（**≈当前**） | 14 |
| 层级深度健康（≤） | 3（真的该极扁） | 4（**≈当前**） | 4–5（可容纳纵深） |
| 层级深度关注（≤） | 4 | 6（**≈当前**） | 6–7 |
| 管理者比健康（≤） | 20%（管理者少、样本小，容忍高） | 15%（**≈当前**） | 15–18%（矩阵/职能可能更高） |
| 管理者比关注（≤） | 30% | 25%（**≈当前**） | 25% |
| 空岗率健康（≤） | 15%（创业期容忍空缺） | 10%（**≈当前**） | 8%（成熟应更紧） |
| 空岗率关注（≤） | 25% | 20%（**≈当前**） | 15% |
| 超编预警占比 | 25% | 20%（**≈当前**） | 15%（成熟超编应更敏感） |

> 这些是**启发式起点，不是行业规范**。必须随预设**显著标注"基准仅供参考，需结合本企业业务阶段校准"**，避免用户把预设当真理。切换后仍可在健康度面板**二次微调**（现有 `setHealthThresholds` 已支持持久化，L163-167）。

**为什么是"阶段"而不是"行业"**：行业差异（如互联网 vs 医院）主要影响**部门形态与管理幅度分布**，但同样规模的互联网公司和医院，"管理者比/空岗率"的**健康值差异没那么大**；真正拉开差异的是**企业阶段**（扁平度、对空缺的容忍度、是否刻意加管理层级）。所以**先做阶段，行业维度留到 v2.0.9 之后再评估**（可复用"情景基准"的切换框架，把"行业基准"作为后续多组预设接入）。

## 3. v2.0.8 HR 价值优先级

### 若 v2.0.8 只做工程收口，HR 用户得到了什么 / 缺什么
- **得到**：数据被安全处理（xlsx 高危项处置）、构建稳定（Tailwind/Vite 收口）、可发布——**信任与可用性**，这是 HR 把真实组织数据放进去的前提。
- **缺**：①口径可解释性；②阶段基准；③导入异常的可读错误；④**示例数据的真实诊断感**（现在模板全绿）；⑤招聘缺口与成本视图；⑥职级差距的可达性。这些是实现"真正用于职场诊断与汇报"的**显著价值缺口**。

### 小而高价值、应纳入 v2.0.8 的 HR 能力（P0/P1/P2 排序）

| 优先级 | 能力 | 对 HRBP/OD 的实际价值 | 实现成本分级 | 是否纳入 v2.0.8 |
| --- | --- | --- | --- | --- |
| **P0** | 诊断口径说明（4 指标公式 + 失真点 + "为什么这条不是问题"） | 防止 HRBP 把被稀释/被深链带偏的指标写进给高管/客户的报告；**当下最缺的可解释性** | 主要是文案（配置/文案） | ✅ 应纳入 |
| **P0** | 未配置数据呈现修正（"未配置编制"从黄色关注→灰色"无数据"） | 消除"没填数据被当成问题"的信任坑；与 README 承诺一致 | 小逻辑 + 标签（低风险前端） | ✅ 应纳入 |
| **P0** | 企业阶段情景基准预设（初创/成长/成熟，可切换） | 让诊断匹配企业阶段，减少"初创被压扁/成熟被误判过深" | 数据对象 + 切换器（配置为主） | ✅ 应纳入（只做阶段，不做行业） |
| P1 | 示例/行业模板补齐编制与职级成本 | 载入模板后直接呈现真实红黄绿，一举看清诊断与缺口成本；**显著降低首次体验的上手成本** | 数据 + 配置（低成本） | 建议纳入 |
| P1 | 导入异常的可读错误 + 字段说明（哪些必填/可选、多少行未匹配部门） | 面向 HR 的友好报错，替代"解析员工文件失败"这种通用 toast（App.tsx L195-197） | 新校验逻辑（前端，中） | 建议纳入或 v2.0.9 |
| P1 | （小步）招聘缺口与成本视图 | 复用现有 L3 `gap`/`gapCost`，以"部门缺口 + 缺口月成本"汇总卡/表格呈现，供招聘 BP 取数 | 主要是编排已有数据（低-中） | 建议 v2.0.9（依赖上述字段梳理） |
| P2 | 职级差距可达性优化（导入目标职级，替代 window.prompt） | v2.0.5 已有"员工职级差距"能力，但目前靠**逐人 window.prompt**（DepartmentCard L216）不可规模化 | 新数据字段（依赖 xlsx 替换） | 延后 v2.0.9 |
| P2 | 管理者比剔除兼岗/副职/外部负责人 | 提高管理者比可信度 | 新数据字段/逻辑 | 延后 v2.0.9 |

**给 v2.0.8 的建议收缩范围**：只把 3 个 P0 项并进 v2.0.8（口径说明、未配置数据呈现、阶段情景基准），它们**不依赖 xlsx 替换、不动数据模型、风险低**，且正好回答"如果这版只做工程收口，HR 会缺什么显著价值"的缺口里最便宜、最要紧的部分。P1/P2 明确排到 v2.0.9，避免挤占工程收口的验收空间。

> 注意：P0 第 2 项（未配置数据呈现）依赖一个**当前行为偏离 README 的修正**——`deptStatus` 对 `headcount===null` 返回 `warn`（L314），而对应建议是 `info`（L746-755）。改状态会牵动 `computeL1`/`computeL3`/`HealthDrawer` 的 StatusDot 呈现与相关单测，建议在 v2.0.8 内**单独立项、附带测试**。

## 4. HR 用户旅程建议（导数据→看诊断→出报告）

**理想路径**：导入真实数据（编制/成本/部门一并进来）→ 选企业阶段情景基准 → 红黄绿定位问题部门 → 逐条可解释建议 → 一键出可交付报告。

**当前实际断点**：

1. **数据字段对齐（最大断点）**：`parseEmployeeExcel`（excel.ts L38-54）只读取姓名/工号/职级/岗位/一级~六级部门，**不含编制、个人成本、目标职级**。因此：
   - 空岗率、编制缺口需要 HR 在健康度 L3 表**逐部门手录编制**（HealthDrawer L402-413）；
   - 成本靠**另一套职级成本配置**（`costForLevel` L221-224）映射，而非员工自带成本；
   - 职级差距靠**逐人 window.prompt**（DepartmentCard L216）。
   结果：一份真实 HR 的编制/成本表**无法一站式导入**，诊断数字易与来源系统打架。→ **建议 v2.0.9 支持在导入时可选识别"编制/成本/目标职级"列**（配合 xlsx 替换落地）。

2. **口径是否易懂**：指标有简短 verdict，但**没有"怎么算的、有什么坑"的口径说明**。HRBP 易把"平均管理幅度 6·适中"直接引用，而不知道它被 40 人直管部门稀释。→ **P0 口径说明**（一段文字 + 报告/抽屉里的"口径与边界"折叠块）即可。

3. **报告是否可解释**：诊断报告（DiagnosticReport.tsx）是纯视觉 + 简短 diagnose/verdict，**没有失真提示、没有"未配置数据为何是黄色"的解释**，且把"未配置编制"显示为黄色（L199-204 用 STATUS_STYLE 渲染整体状态；部门明细、L3 亦如此）。→ **P0 未配置数据呈现修正** + 报告里补"口径与边界"。

4. **是否有示例数据降低上手成本**：OnboardingOverlay + 行业模板存在（OnboardingOverlay L86-91、industryTemplates.ts），但**模板都没有填编制/职级成本**，加载后健康度基本全绿，看不出诊断、缺口、成本的价值。→ **P1：给模板补齐编制与职级成本**，让"载入示例"立即呈现真实红黄绿 + 缺口成本。这一步成本极低，却直接决定 HR 用户能否"一眼看懂这个工具干嘛的"。
