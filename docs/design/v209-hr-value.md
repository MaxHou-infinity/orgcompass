# OrgCompass v2.0.9 · HR 领域视角：口径修正的 HR 语义、阈值标定与场景对比汇报价值

> 作者：hr-expert（团队 v209-roadmap）· 面向 HRBP / OD 用户。
> 依据当前仓库实测：`src/utils/analytics.ts`（`computeL2` / `computeTreeDepth` / `METRIC_CALIBER_NOTES` / `STAGE_PRESETS` / `HealthThresholds`）、`src/types/index.ts`、`src/components/DiagnosticReport.tsx`、`docs/v208-hr-value-audit.md`、`docs/v209-v300-version-plan.md`。
> 定位：本文只覆盖三件事——**HR 语义、阈值标定、场景对比汇报价值**。中位数 / P50 / P90 / 兼岗·副职·外部判定的**计算方案**由 analytics-expert（t2）出；产品范围与验收由 product-expert（t1）出。本文给的是「为什么这么改、改完数字怎么读、给谁看、值不值」。

---

## 0. 一句话结论

v2.0.9 的口径修正，对 HR 不是"把数字算得更准"的技术洁癖，而是**把诊断从"能看"变成"敢写进汇报"**：

- 均值 → 中位数 + 极值：让"管理幅度适中"这句话**扛得住一个 40 人直管部门的追问**；
- 最大层 → P50/P90 + 深链定位：让"层级偏深"不再被**一条业务必需的深链**一票否决；
- 管理者比剔除兼岗/副职/外部：让"头重脚轻"的结论**不再冤枉挂名/外部负责人**；
- 场景对比 + 管理层报告：让 HRBP 汇报组织调整时**第一次能回答"调了什么、为什么调、调了会怎样"**。

---

## 1. 口径修正的 HR 语义（改什么 → 为什么 HR 在乎 → 防止什么误判）

### 1.1 管理幅度：均值 → 中位数 + 极值 + 部门明细，并把"直属"从"节点直挂"修正为"下一层子部门负责人 + 直挂 IC"

**现状（`computeL2` L450-472）**：有负责人部门的"节点直挂员工数"之和 ÷ 有负责人部门数 = 平均直管。两个失真：

1. **均值被极端值稀释**（40 人部门 + 几个 2 人部门 → 平均"适中"）。
2. **"直属"只算节点直挂员工**（`d.employees`），多层导入组织里员工落在叶子节点，**中间管理层的直管人数被系统性低估**，甚至误报"负责人无人直管"（critical）。

**HR 语义**：管理幅度是 HRBP/OD 判断"汇报线是否合理、要不要拆/并部门"的第一指标。它必须回答两个不同的问题，而**均值只回答了半个、且答错**：

- "典型情况"——一个经理通常直管几个人？→ 用**中位数**回答（不被极端值带偏）。
- "有没有失控点"——有没有哪个经理直管过多/过少？→ 用**最大值/最小值 + 部门明细**回答（均值/中位数都会抹掉它）。

**关于"直属"口径（HR 重点，最易被低估）**：标准组织图里"管理幅度 = 直接汇报给你的人"，即**下一层子部门负责人 + 节点直挂 IC**。当前只算后者，导致多层组织（制造/医院/教育/成熟集团）的中间管理者被当成"无人直管"。这个修正**不需要岗位模型**（子部门 = `children`、子部门负责人 = `child.leaderId/Name`、直挂 IC = `d.employees`，均可现算），应和"中位数化"一起在 v2.0.9 落地；否则"中位数化"后仍会系统性低估中间管理层。

> 风险提示：改"直属"口径后，多层组织的管理幅度数字会**明显变大**（一个"0 直管"的经理会变成"4 子部门 + 1 IC = 5"）。必须在口径说明里写清楚，避免用户误以为"数据变差了"。

### 1.2 层级深度：全组织最大路径 → P50 / P90 + 最深链定位

**现状（`computeTreeDepth` L545-552）**：取树的最大路径层数，一条深链决定全组织结论。

**HR 语义**：层级深度要回答的是"**这个组织普遍几层**"（结构是否扁平），而不是"最深的一根枝有多长"。零售/医院/教育天然有"总部-区域-门店/校区"的深链，但 90% 的部门可能只有 3 层。用 max 下结论，会诱发 HRBP **无区别地压层级**，破坏业务必需的纵深。

修正后三件套：

- **P50 = 典型深度**（背景信息，回答"普遍几层"）；
- **P90 = 深尾深度**（主判据，回答"最深的 10% 有多深"）；
- **max + 定位**（回答"最深链是哪条、在哪个部门"，供人工判断是否业务必需）。

> HR 判据的核心转变：灯号应从"max"改到"P90"——"是否普遍过深"看 P90；"是否有个别超深链路"看 max 并**定位出来**，而不是直接判全组织红。

### 1.3 管理者比：剔除兼岗/副职/外部负责人 + 分母对齐到"非管理员工"

**现状（`computeL2` L486-499）**：去重负责人数 ÷ 员工总数（**含管理者本人**）。三个失真：①分母含管理者；②分子未区分专职/兼岗/副职；③负责人可能指向组织外的人（记入分子、不在分母）→ 抬高比值。

**HR 语义**：HRBP 说"管理者占比 15%"时，直觉是"每 6 个干活的人配 1 个管理者"（管理者 ÷ 非管理者），而不是"管理者占全员的 15%"（成本视角）。当前口径是后者，还混入了挂名/外部负责人，导致：

- 一个 200 人、30 管理岗的组织，当前算 15%（÷全员），但 HR 直觉的"扁平度"是 30÷170 ≈ 17.6%；
- 兼岗/外部负责人会让"头重脚轻"的结论**冤枉**真实情况。

修正方向：

- **分子**：只计"专职 + 内部 + 非副职"负责人（去重）。其中"外部"可自动判定（leader 不在员工表）、"兼岗"去重已做但需区分"真兼岗 vs 挂名"、"副职/挂名"需显式标记。
- **分母**：对齐为"非管理员工"（全员去虚拟 − 上述专职负责人）。主展示"管理者 ÷ 非管理者（%）"，UI 标注等价表述"≈ 每 X 名员工配 1 名管理者"；报告里附"管理者 ÷ 全员（%）"作为管理成本占比的第二读数。
- **数据模型**：需要一个**可选、向后兼容**的负责人类型字段（如 `leaderType?: 'fulltime' | 'concurrent' | 'deputy' | 'external'`，缺省按 `fulltime` 处理），`.orgproj` 无需升版本号。这是 v2.0.9 唯一的小数据模型补充，不阻塞 v2.1.0 岗位模型。

### 1.4 空岗率：v2.0.8 已对齐口径，v2.0.9 只补"编制真实性"提示

空岗率分子分母已在 v2.0.8 对齐（`computeL2` L501-534），v2.0.9 不重复计算改动。但 HR 语义上仍有一个**代码解不了的坑**：空岗率对"编制是否真实"极度敏感——僵尸编制（为预算填、实际不招）会虚高空岗率，战略储备编制会虚高缺口，只能靠 HR 自证。建议 v2.0.9 在空岗/超编建议里保留并强化一句提示："请确认是战略储备还是冗余"，口径说明补一句"编制是否真实填写由 HR 确认"。

## 2. 阈值标定（修正后口径的灯号判据 + 建议值）

> 核心原则（HR 视角）：**口径变了，灯号"看哪个统计量"也要变**。否则改了计算、阈值却还套在旧统计量上，会产出新的误判。

### 2.1 管理幅度（中位数 + 极值触发）

灯号判据分两级：

1. **主判据（中位数）**：中位数落在 `[spanHealthyMin, spanHealthyMax]` 为健康；低于下限或高于上限为关注/预警——**沿用现有三档区间**（初创 2–7 / 成长 3–8 / 成熟 5–9），因为中位数本来就该落在健康带中央。
2. **极值触发（新增，防"中位数掩盖单点失控"）**：`spanMax`（各部门直管最大值）> `spanWarnMax`（初创 10 / 成长 12 / 成熟 14）→ 至少升级为"关注"；`spanMax` ≥ 关注上限 × 1.5 → "预警"。`spanMin ≤ spanWarnLow(1)` 的部门单独列"无人直管/直管过少"清单（改"直属"口径后，多层组织的误报会大幅减少）。

> 展示：面板主指标显示"中位数 X 人"，旁边给"最小–最大"与"超过关注上限的部门数"；点击进入部门级明细（每部门直管数，可排序）。

### 2.2 层级深度（P50 / P90 / max）

灯号判据：

1. **主判据（P90）**：P90 ≤ `depthHealthyMax`（初创 3 / 成长 4 / 成熟 5）健康；≤ `depthWarnMax`（4 / 6 / 7）关注；> 关注上限预警。**沿用现有阈值、直接作用于 P90，无需新增配置项。**
2. **硬上限触发**：`max` > `depthWarnMax + 2`（如成长档 >8 层）→ 预警（单条过深链路本身是治理信号，即使少见）。
3. **定位**：无论灯号，最深链都定位到具体部门/路径，供 HR 判断"是业务必需还是该压"。

> 阈值建议（P90 作用于）：初创 P90≤3 / 成长 P90≤4 / 成熟 P90≤5；关注上限 4 / 6 / 7；硬上限 max 6 / 8 / 9。与现有 `STAGE_PRESETS` 的 `depthHealthyMax`/`depthWarnMax` **一一对应，不改配置结构**。

### 2.3 管理者比（剔除后、÷非管理员工）

主口径改为"专职负责人 ÷ 非管理员工（%）"。换算：`÷非管理 = ÷全员 / (1 − ÷全员)`。建议阈值：

| 阶段 | 健康（÷非管理）≤ | 关注 ≤ | 等价"÷全员"参考 | 等价"1:N" |
| --- | --- | --- | --- | --- |
| 初创 | 25% | 43% | 20% | 1:4 |
| 成长 | 18% | 33% | 15% | 1:5.5 |
| 成熟 | 22% | 33% | 18% | 1:4.5 |

> 说明：这些是启发式起点、需结合企业实际校准；"÷全员"列是给 HR 对照成本视角的参考。成熟期职能/矩阵组织允许略高的管理者比。

### 2.4 空岗率 / 超编

阈值沿用 v2.0.8 三档（初创 ≤15 / 成长 ≤10 / 成熟 ≤8；超编预警占比 25%/20%/15%），不改值，只补"战略储备 vs 冗余"提示（见 §1.4）。

## 3. 场景对比 + 管理层报告的价值（README Now #2）

### 3.1 HRBP 汇报的真实痛点

组织调整类汇报最难的不是"画出新方案"，而是**讲清三件事**：调了什么、为什么调、调了之后会怎样。当前工具只能看单个场景的红黄绿，HRBP 要自己拿着"基线 vs 方案A"逐张截图对比，数字对不上、话讲不清，管理层难以拍板。

### 3.2 场景对比应该比什么（HR 视角）

1. **四项指标 + 整体诊断**并排对比（每项：数值 Δ + 红黄绿 Δ + 一句话判读 Δ），并**沿用修正后的口径**（中位数/P90/剔除后管理者比），否则对比出来的"改善"不可信。
2. **部门级差异**：新增/删除/移动/改汇报线的部门，负责人变化，编制/实际/缺口/缺口成本的变化（Δ），谁变红谁变绿。
3. **人员流动**：谁换了部门、谁换了汇报线、谁新增/移除（含兼岗、未入架构员工）。
4. **缺口与成本汇总**：总缺口、总缺口成本、管理者比变化带来的管理成本变化——给管理层"这方案省/花多少钱、补多少编制"的抓手。

### 3.3 管理层报告应该长什么样（HR 视角）

- **一页纸结论**：整体健康度 + 3~5 条关键变化 + 建议动作，管理层 30 秒能看懂；
- **可追溯**：每个对比点能点回具体部门/人员，不是黑盒结论（保持"可解释、可追溯"的既有承诺）；
- **必带"口径与边界"段**：复用并更新 `METRIC_CALIBER_NOTES`（修正后），防止管理层把"中位数 6 人"当"每个经理都 6 人"、把"P90=4"当"没有深链"；
- **本地优先**：本地生成、可导出 PNG/Excel/报告，不引入云端/遥测（与产品原则一致）。

### 3.4 验收建议（HR 视角，供 product-expert 融合进 t1）

- 能对"基线 vs 方案A vs 方案B"输出可读的指标/部门/人员差异，且每项差异可追溯到具体部门/人员；
- 报告含"口径与边界"段且与修正后口径一致；
- `.orgproj` 与导出产物兼容，不破坏现有场景数据。

## 4. 给团队的落地建议与边界

1. **优先级**：口径修正（§1、§2）先于场景对比（§3）——对比的前提是数字可信，否则比出来的是"两个错误数字的差"。
2. **与 t2（analytics）的边界**：中位数/P50/P90 的计算、兼岗/副职/外部的自动判定规则、"直属=下一层子部门负责人+直挂 IC"的精确定义，由 analytics 定方案；本文只定"语义 + 阈值 + 判据 + 展示"，避免两处给出冲突的阈值。
3. **与 v2.1.0 的边界**：负责人类型字段是**可选、向后兼容**的小补充（缺省 fulltime），不依赖、也不阻塞 v2.1.0 岗位模型；"管理幅度=整棵子树控制跨度"这类需要岗位模型的深化定义，留给 v2.1.0。
4. **风险**：改"直属"口径后多层组织数字会跳变，必须同步更新 `METRIC_CALIBER_NOTES`（`analytics.ts` L563-568）与 README「诊断如何工作」表，否则"数据变差了"会先于"口径更准了"到达用户。
