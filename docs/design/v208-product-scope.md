# OrgCompass v2.0.8 — 产品视角：范围、验收标准与风险边界

> 作者：产品专家（product-expert）
> 定位：本文件只描述 **产品 / 用户 / 验收** 视角。技术实现细节（选哪个库、构建配置、签名、回滚脚本）由 security-build-expert 负责，本文件仅在结论处与之对齐。
> 用途：可直接并入 `docs/v208-roadmap.md`，作为 v2.0.8 的产品侧收口。

## 0. 一句话定位

v2.0.8 是 **「信任与稳定性收口版本」**，不是功能大版本。它对用户交付的核心价值是一句话：**你导入的组织数据更安全、出错时更清楚，升级之后还能看到和以前一样的东西。** 一句话里藏了三件事：**更安全**（依赖安全处置）、**更清楚**（导入校验与错误解释）、**不变差**（升级后用户可感知的功能与界面一致）。

## 2. 面向用户的验收标准清单

> 下列每一条 **用户可感知**，且 **可核对 / 可观测**。验收动作写在方括号中，由 QA 或产品验证。

### 2.1 更安全（安全处置的用户可感知结果）

- **S1** 导入一个**格式合法、结构异常**的 Excel（例如缺列、空表、首行不是表头），用户收到**一句话说清楚"哪里不对、怎么改"**的错误提示，而不是程序崩溃、白屏或生成无法回退的空组织树。
  - [验收] 用缺「姓名」列的员工表、全空表、首行无表头的表分别导入，观察提示是否指向具体缺失项并给出修正建议；全程不出现崩溃或不可回退的空树。
- **S2** 导入一个**超大或异常工作簿**时，用户收到**明确的处理提示或限额说明**，而不是界面卡死。
  - [验收] 构造超过提醒阈值与硬上限的两个文件，分别观察是否出现"可能较大，处理可能变慢"提示 / 超限明确拒绝，且应用保持可交互。
- **S3** 导入入口出现**明确的本地处理微文案**（例如"本机处理，数据不出设备"），用户能据此建立信任。
  - [验收] 在导入对话框或导入后的首屏看到该文案；确认表述**不夸大**（不承诺"绝对无风险"，见 §3 话术）。
- **S4** 完成 xlsx 处置后，**导入行为体验与升级前保持一致**（读列、映射、生成组织树的结果不变）。
  - [验收] 用一套标准样例 Excel 在升级前后各导入一次，对比生成的部门树与员工归属**完全一致**。

### 2.2 更清楚（导入校验与错误解释）

- **C1** 用户能区分「文件本身有问题」与「文件格式不符」。例如：扩展名不支持 → 明确提示；内容缺列 → 明确指出缺哪几列；数据自相矛盾（如一部门两负责人）→ 指出冲突点。
  - [验收] 分别用 .csv 误传、缺列、同部门双负责人三类文件导入，观察提示是否精准指向根因而非笼统报错。
- **C2** 错误提示**可行动**：提示里包含「下一步怎么做」，例如"请按模板补齐至少：姓名 / 一级部门 / 工号"。
  - [验收] 检查提示文案是否给出可执行的补齐/修正指引，而非仅有"解析失败"。
- **C3** 导入得到**可回退**的失败：失败后不影响用户当前已打开的项目，能回到导入前的状态。
  - [验收] 制造一次失败导入，确认当前项目内容未被破坏、可正常继续编辑。

### 2.3 口径可解释（诊断指标不被误读）

- **M1** 健康面板 / 诊断报告中，4 项指标的**计算口径**可用一段话或一个"?"说明讲清楚（怎么算的、不含哪些数据、不等于什么）。
  - [验收] 打开健康面板，对每项指标能看到口径说明；导出的诊断报告也含一段「口径与边界」说明。
- **M2** 未配置编制的部门，**明确显示"无法计算"而非绿/黄/红**，不把缺失数据伪装成健康结论。
  - [验收] 构造编制为空或全部为"未配置"的场景，确认显示为 info 提示而非健康状态灯。
- **M3** 超编与空岗**作为两个独立信号呈现**，不互相掩盖（一个岗位超编、另一个岗位空岗不应互相抵消成一个"正常"）。
  - [验收] 构造同部门不同岗位"一超编一空岗"，确认两个信号同时可见，不会被合并成一个中性结论。

### 2.4 不变差 / 无回归（升级后用户可感知一致）

- **R1** 升级后，用户**当前可见的功能入口、界面布局、交互方式都保持原样**（即便底层换了 Tailwind/Vite/解析库）。
  - [验收] 升级后走一遍核心路径：导入 → 建树 → 看健康度 → 多场景 → 导出 PNG/Excel/报告，对照升级前**逐项一致**。
- **R2** 视觉回归通过：关键页面（健康度面板、组织图画布、导入弹窗）样式与升级前一致，无配色/布局/字体漂移。
  - [验收] 对关键页面做升级前后截图比对，差异为零或为已确认的可接受微调。
- **R3** 用户已有的 `.orgproj` 项目文件**升级后可正常打开**，导出产物格式不变。
  - [验收] 用升级前保存的项目文件在升级后打开，内容与导出格式一致。

## 3. 产品风险边界：xlsx 处置的用户呈现方式

### 3.1 何时提示用户

风险边界不是靠"弹大告警框"呈现，而是分三层，**只在相关时刻出现**，避免打扰：

| 时机 | 呈现物 | 目的 |
| --- | --- | --- |
| 常驻（导入入口） | 一句微文案："本机处理，数据不出设备" | 建立"本地优先"的信任基线 |
| 导入前（前置校验） | 扩展名 / 大小 / 格式校验，超限或非法时给清晰提示 | 把异常挡在解析之前，避免卡死或误解 |
| 解析异常时 | 精准错误提示 + 可行动指引（见 §2.1/§2.2） | 让失败可理解、可回退 |

**不做**：不做"每次导入都弹长段安全声明"，不把安全做成打断工作流的前置弹窗。

### 3.2 是否做上传前校验：做（轻量、非阻塞）

- **扩展名**：引导用户使用受支持的 `.xlsx`（可评估是否放宽到 `.xls`）；遇到明确不支持的格式给出"请另存为 .xlsx"提示。
- **文件大小**：软提醒阈值（例如 >10MB 提示"文件较大，处理可能变慢"），硬上限（例如 >50MB 明确拒绝并说明原因），避免本地解析卡死。
- **结构校验**：核对必要的表头列（姓名、一级部门等）是否存在，缺失时给出"缺哪几列 + 怎么补齐"的提示，而不是静默产出空树。

> 说明：这些是「输入护栏」，目标是**降低暴露面 + 提升可解释性**，不是承诺能拦截一切恶意文件（见下）。

### 3.3 "本地处理所以安全"的用户话术：用，但别夸大

**对的表达**（可信、不过度承诺）：
> "你的组织数据只在你本机处理，不会上传到任何服务器；导入前我们也会做基本的格式与大小校验。"

**避免的表达**（过度承诺，会反噬信任）：
> "完全安全 / 绝对无风险 / 任何文件都不会有问题。"

平衡点：本地优先 + 输入校验是**真实的安全增量**，可以讲；但"恶意构造的工作簿仍可能造成本地解析异常/卡顿"这一边界要认真对待，用"降低风险"而非"消除风险"的口径。**不要在话术里承诺"我们替你免疫了所有恶意文件"。**

### 3.4 数据隐私提示

- v2.0.8 只需在**导入入口**给一句微文案，不必单独建"隐私声明页"——README 已有完整「数据与隐私」章节，且本版本不引入遥测/上传。
- 提示覆盖三点：①本地处理，②不自动上传/同步，③导出产物（PNG/Excel/报告）由用户自行管理、用在企业认可的设备与存储上。

## 4. 诊断指标的用户口径审视

### 4.1 结论：作为「结构性信号」足够严谨，作为「管理评分」会被误读

4 项指标（管理幅度 / 层级深度 / 管理者比 / 空岗率）作为**发现值得讨论的结构性信号**是合适且可解释的，这点符合产品定位（README 已声明"指标用于发现值得讨论的结构性信号，不替代业务背景、人才判断"）。但**如果直接当成管理层的"体检评分"甩给管理者，存在被误读的风险**，主要风险点如下。

### 4.2 各指标的误读风险与建议

| 指标 | 当前口径 | 潜在的误读风险 | v2.0.8 的口径说明要点 |
| --- | --- | --- | --- |
| 管理幅度 | 有负责人部门的直属员工总数 ÷ 有负责人部门数 | 是**均值**，会掩盖分布：一个主管带 15 人、另一个带 1 人，均值可能"看起来很健康"。且只统计"有负责人"的部门，若很多部门无负责人，分母变小、幅度被抬高。 | 说明这是"平均值"，不反映单点失衡；建议同时看**按部门的幅度分布**或异常标记。 |
| 层级深度 | 组织树从 L1 起的最大层数 | 深度≤4 一般为宜，但**科层/矩阵/医院**等可能是刻意的深结构。深度只数"层"，不反映每层人数。 | 说明这是"最大层级数"，不评估分层合理性；深结构需结合行业场景判断。 |
| 管理者比 | 去重后的部门负责人数 ÷ 员工总数 | 负责人按部门去重，若一人兼多部门，比例会被「拉平」。且分子/分母是否包含负责人自身会影响比值，需明确口径。 | 说明"负责人数（按人去重）÷员工总数"，并注明管理人员是否计入分母。 |
| 空岗率 | （有效编制数 − 实际人数）÷ 有效编制数 | 若实际人数>编制 → 出现**负空岗**，实为超编；若编制未配置 → 无法计算，不能伪装成健康。 | 说明"有效编制"的排除项；空岗与超编**分开**呈现，超编用梯度预警（>20%）。 |

### 4.3 超编梯度与未配置编制

- **超编梯度 >20% 预警**：作为独立的、与空岗区分的信号保留。**不要与空岗率合并成一个"人员配置健康度"**，否则会互相掩盖（一岗位超编、一岗位空岗不该抵消成"正常"）。
- **未配置编制按 info 提示**：这是正确的**不夸大**原则，保留。未配置 → 显示"无法计算原因"，不参与健康判定。

### 4.4 v2.0.8 给用户的口径能力：轻量，不做完整基准体系

- **做**：给一个**轻量的口径说明**——健康面板每个指标旁一个"?"说明（怎么算的、含哪些/不含哪些数据、不等于什么），并在**导出的诊断报告**里附一段「口径与边界」说明。让用户和下游管理者拿到报告时**能解释、能追溯**。
- **不做**：v2.0.8 **不建可复用的行业/企业阶段诊断基准**（那是 README Next 项）。理由：基准需要大量数据积累与标定，与"先收口"的定位冲突；先确保口径透明，基准留到后续版本。

## 5. 优先级建议（从用户价值视角重排）

### 5.1 先把 P0/P1 归好类：技术债收口 vs 用户价值

| 原优先级 | 事项 | 本质 | 对用户的价值 | 建议 |
| --- | --- | --- | --- | --- |
| P0 | xlsx 高危依赖 | **技术债收口 + 信任/安全** | 高（用户上传敏感组织数据，解析高危是真实的信任与安全风险） | **必做**。v2.0.8 的第一优先级。 |
| P1 | Tailwind 4 迁移 | 纯技术债收口 / 构建稳定性 | 无直接可见价值（防回归） | **必做**，作为"构建回归"收口，独立可回滚。 |
| P1 | Vite 8 / React 插件 6 | 纯技术债收口 / 工具链 | 无直接可见价值（防打包回归） | **必做**，独立可回滚。 |
| （新增） | 数据导入校验与错误解释（README Now #1） | **用户价值** | 高，且与 xlsx 处置同路，边际成本低 | **建议纳入 v2.0.8**。这是本版本最有用户价值的一项，且不引入额外风险。 |
| （新增） | 诊断指标口径说明 | 用户价值（可解释性） | 中高（防止交付物被误读） | **建议纳入 v2.0.8**（轻量）。 |
| （新增） | 安装/升级/示例体验对齐（README Now #3） | 用户价值 + 发布侧优化 | 中 | **单列并入** v2.0.8（文档/发布侧）。 |
| README Now #2 | 场景差异比较与管理层报告 | 用户价值（较大特性） | 高 | **推迟**。若 P0/P1 完成后有余量再评估；否则进 v2.0.9。 |

### 5.2 结论

v2.0.8 的组合建议：

1. **收口必做**（P0 安全 + P1 两个构建/工具链），它们是"技术债收口"，先把发布稳定性与安全隐患清掉。
2. **同路捎带一个最高用户价值项**：数据导入校验与错误解释 + 风险边界呈现（§1.1 A/B）。它为什么放 v2.0.8？因为**我们本来就要为处置 xlsx 而改动导入链路**，在改动的同时把"校验+错误解释+本地处理文案"加进去，边际成本最低、收益最大，且是用户最痛的导入痛点。
3. **轻量可解释**：诊断指标口径说明（§1.1 C）作为低成本的"防误读"增强。
4. **推迟**：场景差异与报告（README Now #2）推迟到 v2.0.9，保持 v2.0.8 的"收口不膨胀"纪律。

> 强调：**v2.0.8 不因"顺手"而膨胀。** 凡不属于"依赖安全 / 构建稳定 / 发布可靠 / 导入可信"的扩展性功能，一律推迟，避免把收口版本做成大杂烩。

## 6. 风险与沟通话术（xlsx 三种处置路径的用户口径）

> 三种路径的用户沟通，共同内核是：**数据不出本机 + 本地只读解析 + 输入校验**。**避免使用"绝对无风险"的过度承诺。** 下列话术可按实际处置结果选用。

### 6.1 路径 A：替换为维护中的解析库（推荐）

> "我们把读取表格的引擎换成了更稳健、社区仍在维护的版本，导入更可靠；格式异常时会给你更清楚的提示。**你的数据仍然只在你本机处理，不会上传。**"

### 6.2 路径 B：受控 fork / 补丁版本

> "我们使用的表格解析组件社区已停止更新，我们保留了经过谨慎管理的修复版本，功能与体验不变。**数据仍只在本机处理、本地只读解析。**"

> "当前版本仍沿用原有解析组件，但我们已把它限定在**本地只读用途**，并增加了**文件大小与格式校验**来降低暴露面；你可按需升级到后续版本获得更稳妥的解析。**数据仍只在本机处理。**"

> ⚠️ **产品立场**：风险例外**必须是用户可见、有意为之**的决定，不能做成静默默认。选择例外时应：①在发布说明与 README 中**明确披露该残余风险**；②说明为什么暂时无法消除；③给出升级路径。**把一个已知高危依赖悄悄保留且不向用户交代，是最伤害信任的做法。**
