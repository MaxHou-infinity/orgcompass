# OrgCompass v2.0.9 开发路线图（补充完善版）

> 状态：候选路线图（已由团队 v209-roadmap 三视角产出并融合，Captain 已裁决跨视角冲突）。
> 目标：在继续深入「岗位化」之前，先**把已有 4 项诊断指标算对**（口径可信化），并交付**唯一一个新特性**——场景差异比较与管理层报告（README「Now」第 2 项）。
> 一句话承诺：**导入已安全、升级后所见不变（v2.0.8 收口）之外，现在连「基线 → 方案 A 到底变了什么、变了多少、值不值得讨论」也能一眼看清、一键交付。**

## 0. 定位与范围原则

**v2.0.9 = 「口径可信化」补丁（patch）**，不是功能大版本。它回答两个问题：

1. 已有 4 项指标「算对了吗」——修掉被 HR 审计（[v208-hr-value-audit.md](v208-hr-value-audit.md) §1）点名的三处失真：管理幅度被均值稀释 + 中间管理层低估、层级深度被一条深链一票否决、管理者比被挂名/外部负责人抬高。
2. 多场景「差异看得见吗」——交付场景差异比较 + 管理层报告，让 HRBP 汇报组织调整时第一次能回答「调了什么、为什么调、调了会怎样」。

> **纪律（沿用 v2.0.8）**：v2.0.9 **不动数据模型、不新增持久化字段、不新增 HealthStatus 状态、不改空岗率计算、不重标定已发布的阶段预设阈值**。凡属「数据模型/岗位化/胜任度」的扩展一律推后到 v2.1.0+。三视角一致同意此边界。

## 2. 诊断口径修正（三处，含 Captain 裁决）

> 算法细节、伪代码、测试清单见 [v209-analytics-caliber.md](v209-analytics-caliber.md)；HR 语义与阈值依据见 [v209-hr-value.md](v209-hr-value.md)。本节只给**定案口径**（Captain 已裁决跨视角冲突）。

### 2.1 管理幅度（A）

**直管人数 `directReports`**（修中间管理层低估）：

```
directReports(dept) = 节点直挂非虚拟 IC 数 + 下一层「有负责人」子部门数
```

**聚合与灯号**（修均值稀释）：

- `span.value` 由「算术平均」改「**中位数**」，`span.status = spanStatus(median, thresholds)`，阈值 `spanHealthyMin/Max`（初创 2–7 / 成长 3–8 / 成熟 5–9）**不变**。
- **极值升级**：`spanMax > spanWarnMax`（10/12/14）→ L2 至少升「关注」；`spanMax ≥ spanWarnMax × 1.5` → 「预警」。
- **部门级明细**：`spanBreakdown.distribution` 列出每个有负责人部门的直管数（降序）；`generateDeptSuggestions` 的「偏窄/偏宽/无人直管」判定**统一改用 `directReports`**，最宽部门标 critical（不再被中位数抹平）。
- `spanBreakdown.mean` 保留作参考（不参与判定）。

### 2.2 层级深度（B）

**Captain 裁决：灯号从「max 主判」改「P90 主判 + max 硬上限」**（t2 主张保留 max 主判，t3 主张 P90 主判；采用 t3，理由见 §5）。

- 统计对象 = **所有部门节点**的深度（非叶路径）；P50 取中位、P90 取 **nearest-rank**（`index = ceil(0.9·n) − 1`，整数层）。
- **主判据（P90）**：`P90 ≤ depthHealthyMax` 健康 / `≤ depthWarnMax` 关注 / `>` 预警，阈值沿用 `depthHealthyMax/depthWarnMax`（3/4/5、4/6/7）**不变**。
- **孤立深链升级**：`max > depthWarnMax` → 至少「关注」（即使 P90 健康），并定位最深链路径。
- **硬上限**：`max > depthWarnMax + 2` → 「预警」（单条过深链路本身是治理信号）。
- `depth.value` 改展示 **P90**（主），`depthBreakdown` 附 `max / p50 / p90 / deepestDeptId / deepestPath`；空树保持现有 `无法评估层级` 文案。

### 2.3 管理者比（C）

**Captain 裁决：分母保留「含管理者全员」主判 + 「非管理者」辅助展示**（t2 主张÷全员、t3 主张÷非管理者并给重标定值；两者健康边界数学等价，采用÷全员主判以零阈值改动，见 §5）。

- **统一去重**：`canonical key = leaderId 优先、其次 leaderName`，修「同一人 id/name 混用双计」隐藏 bug。
- **剔除外部负责人**：负责人 key 不在员工名册（`employeeId`/`name` 命中）→ 判「外部」，不计分子、仅展示 `externalManagers`。
- **暴露兼岗**：同一 key 兼任 ≥2 部门 → `multiDeptManagers` 计数（去重后分子仍算 1，不会虚高）。
- **主口径**：`managerRatio = internalManagers ÷ totalEmployees（含管理者、非虚拟）× 100`，阈值 `managerHealthyMax/managerWarnMax`（20/30%、15/25%、18/25%）**不变**。
- **辅助口径（仅展示）**：`internalManagers ÷ nonManagerEmployees × 100`，等价「≈ 每 N 名非管理员工配 1 名管理者」。
- **副职/挂名精确剔除**：现有字段无法判定，**延后 v2.1.0**（引入 `leaderType`）。判定点 `computeManagerBreakdown` 已写成独立函数，届时替换 internal 判定逻辑即可，不改调用方。

### 2.4 空岗率（D，只补文案）

计算不变（v2.0.8 已对齐）。仅补提示：「请确认是战略储备还是冗余」，口径说明补「编制是否真实填写由 HR 确认」。

### 2.5 口径文案同步

`METRIC_CALIBER_NOTES`（`analytics.ts` L563-568）4 段**必须同步改写**（成品文案见 [v209-analytics-caliber.md](v209-analytics-caliber.md) §D.4），README「诊断如何工作」表同步更新。

## 3. 场景差异比较 + 管理层报告（E，README Now #2）

> 完整产品范围、验收、话术见 [v209-product-scope.md](v209-product-scope.md)。

### 3.1 形态（最低交互成本）

- **锚点模型**：默认「基线 vs 单个目标场景」。基线锚点 = **第一个场景为默认基线 + 可手动切换**（Captain 裁决，不新增「基线标记」字段，压最低复杂度）。**先做「1 vs 1」，不做「N 场景矩阵」**。
- **默认「只看差异」** + 「显示全部」开关。
- **三层结构**：L0 结论条 → L1 四项指标并排（数值 Δ + 红黄绿灯号 Δ）→ L2 部门差异表（增/删/改/负责人/编制成本 Δ）→ L3 人员调动清单。
- **颜色约定（红线）**：方向色（↑↓，蓝色/灰色）与健康色（红黄绿）**分离**，避免「人数下降」被误读为「变差」。

### 3.2 管理层报告 = 多场景推演决策底稿（≠ 单场景体检报告）

8 段结构：报告头（含场景 `updatedAt` 时间戳）→ 一页结论（+建议动作**留白**）→ 四项指标对比（+口径折叠块）→ 部门结构差异 → 人员调动清单 → 缺口成本汇总 → 口径与边界 → 页脚。导出 PNG + 打印/PDF + 差异表 Excel。

### 3.3 关键实现约束

- 指标 Δ **直接复用 t2 的三个 breakdown**（`computeSpanBreakdown / computeDepthBreakdown / computeManagerBreakdown`），**不得重复实现计算逻辑**。
- 场景数据不一致时明确显示「无数据/不可比」，**不把缺失当 0**。

## 6. 评审 / 合规与回滚原则

- **每项独立、可回滚、有验证记录**：三处口径修正（A/B/C）各自独立 commit + 独立测试，不与场景差异（E）捆绑。
- **测试改造是硬约束**：外部负责人剔除会让现有 `analytics.test.ts` 大量 fixture 失效（负责人 `leaderId` 不在员工名册内被判「外部」），**必须同一 PR 同步改造 fixture**，禁止用「跳过测试」合并。
- 口径修正会让老用户看到「数字跳变」，**必须**在口径说明与版本说明里写清「本版本起管理幅度改用中位数 / 层级深度改用 P90 / 管理者比剔除外部」，避免「数据变差了」先于「口径更准了」到达用户。
- 维持本地优先、不夸大、不黑盒评分（沿用 v2.0.8 纪律）。
